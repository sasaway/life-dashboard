# 라이프대시보드 개발 진행 방식

규칙의 기준은 `CLAUDE.md` 와 `design/DESIGN.md` 다. 이 스킬은 그 규칙을 **어떤 순서로** 지키는지 적는다. 둘이 어긋나면 CLAUDE.md 가 맞다.

일은 늘 같은 고리로 돈다: **Cowork 가 프롬프트를 쓴다 → Claude Code 가 계획 · 만들기 · 확인 · 커밋 → 은월이 폰에서 확인 → Claude Code 가 Cowork 에 넘길 글을 쓴다 → Cowork 가 시트 · 브리핑 · 캘린더 · Notion 을 맞춘다.**

## 0. 어떤 일인지 먼저 정한다
| 종류 | 언제 | 버전 | 커밋 | 더 하는 것 |
|---|---|---|---|---|
| 새 기능 | 기능이 생기거나 바뀐다 | 가운데 자리 (v3.0 → v3.1) | `feat(범위): …` | Notion 기능 목록에 있는 것만. 없으면 제안만 한다. 설계를 먼저 이야기하고 하나씩 만든다 |
| 핫픽스 | 버그 · 기본값 맞추기 · 문구 · 화면 다듬기 | 마지막 자리 (v3.0.5 → v3.0.6) | `hotfix(범위): …` | 화면 표시 `vX.Y.Z 핫픽스 · M월 D일` |
| 유지보수 (x.9) | 1.9 · 2.9 · 3.9 … | x.9 | `feat` · `refactor` · `docs` | UI 를 직관적으로 정리 · `CHANGELOG.md` 에 그동안의 요약 · 처음 켤 때 자동 백업(새 저장 칸이 빠짐없이 들어가는지) · git 태그 `vX.9` |
| 기록만 | 문서 · 진행 기록 | 안 올림 | `docs(범위): …` | |

프롬프트가 종류를 적어 줬으면 그대로 따르고, 내용이 그 종류와 안 맞으면(핫픽스라는데 새 기능 · 새 저장 칸이 크다) 계획에서 말한다. 한 번에 하기 크면 버전을 나누자고 제안한다.

## 1. 프롬프트 받기
- 붙여 넣은 글이 문장 중간에서 끊겼으면 `Claude outputs/` 에서 같은 제목의 프롬프트 파일을 찾아 읽는다. 첫 부분이 붙여 넣은 글과 같은지 확인하고, 파일에서 읽었다고 은월에게 말한다. 파일이 없으면 뒷부분을 달라고 한다.
- 프롬프트가 묻는 확인(push 여부 · 칸 이름 등)은 코드와 `git status` 로 확인해서 한 줄로 답한다. 직접 확인하지 못한 것은 추정이라고 말한다.
- 프롬프트 없이 은월이 말로 부탁한 일도 같은 순서로 한다. Notion 에 없는 새 기능이면 만들기 전에 그 점을 말한다.

## 2. 기준선
- `git status --short --branch` 로 브랜치 · 안 올린 커밋을 본다.
- `npm test` 를 돌려 통과 개수를 적어 둔다. 끝날 때 이 숫자보다 줄면 안 된다 (일부러 지운 테스트는 무엇을 왜 지웠는지 적는다).
- Notion 을 봐야 하는 일이면 읽기만 하고, 본 페이지들의 수정 시각을 적어 둔다.

## 3. 계획 (코드를 쓰기 전에)
- 새 기능 · 저장 데이터가 바뀌는 일 · 프롬프트나 Notion 에 "계획 모드" 가 적힌 일은 계획 모드로 들어간다. 글자 하나 고치는 일은 바로 한다.
- 고칠 파일을 직접 읽고 계획에 적는다: 왜 하는지 · 바뀌는 파일 · 저장 칸(새 칸이면 백업) · 폰에 저장된 데이터 옮기기 · 테스트 · 확인 방법.
- 은월에게 묻는 것은 프롬프트가 "묻는다" 고 한 것과, 코드로 답이 안 나오는 선택뿐이다. 선택지 2~4개, 추천을 첫 번째에 둔다.
- 프롬프트에 없던 경우를 발견해 스스로 정했으면 계획이나 마지막 보고에 따로 적는다.

## 4. 만들기
- 기능은 하나씩. 하나가 끝나면 확인 방법을 알려 주고 다음으로 넘어가도 되는지 묻는다.
- 계산은 순수 함수로 `js/<이름>.js`, 화면은 `js/<이름>-view.js`. 있는 부품(`.pin` · `.mark` · `.seg` · `askConfirm`)을 먼저 찾아 쓴다. 의존성 · 빌드 단계는 늘리지 않는다.
- 폰에 저장된 값을 옮길 때는 한 번만 하고 표시를 남기거나, 몇 번 돌려도 같게 만든다. 지난 기록(`mealLog` 등)은 바꾸지 않는다.
- 옛 규칙을 확인하던 테스트는 새 규칙으로 고치고, 규칙마다 테스트를 더한다. 모듈 상태를 바꾸는 테스트는 끝에 되돌린다.
- 새 저장 칸이 생기면 `tests/backup.test.js` 에 백업 → 되살리기 테스트를 더한다.
- 새 `js` 파일은 `sw.js` 의 `FILES` 에 넣는다 (테스트가 확인한다).
- 시트로 나가는 줄을 바꿀 때는 칸 수 · 칸 순서를 그대로 둔다 (Cowork 가 칸 위치로 읽는다). 줄을 더할 때는 맨 아래에.

## 5. 버전 · 문서
- `js/version.js` 의 화면 글자와 `sw.js` 의 `VERSION` 을 같이 올린다.
- `PROGRESS.md`: 완료 목록에 한 줄(무엇을 · 왜 · 은월이 고른 것 · 안 한 것), 바뀌었으면 '기록 시트' 표, '다음 할 일', 다음 Notion 기준 시각.
- 새 부품이 생겼으면 `design/DESIGN.md` 부품 표에 한 줄. 새 색이 필요하면 먼저 은월에게 묻는다.
- `CHANGELOG.md` 는 x.9 버전에서 이어 쓴다. 그 사이 버전은 프롬프트가 말할 때만 짧게.
- 스킬 · 플러그인을 더할 때는 skill-inspector 로 검사하고 `SKILLS.md` 에 적는다.

## 6. 브라우저 확인 (390px · 320px)
- `python3 -m http.server` 로 열고, 끝나면 끈다.
- **먼저 서비스 워커 사본을 지우고 `sw.js` 요청을 막는다.** 안 그러면 옛 버전 화면을 보고 "안 바뀌었다" 고 착각한다. 화면의 버전 글자가 새 버전인지부터 본다.
- 시계는 Playwright `page.clock.setFixedTime` 으로 옮긴다. 저장값은 `ld:` 로 시작하는 localStorage 칸에 넣는다.
- 확인 창 버튼은 순서가 아니라 글자(`지우기` · `되돌리기`)로 누른다. 설정 톱니는 메인 화면에만 있다.
- 보는 것: 바뀐 화면 · 옛 저장값으로 열었을 때 · 새로고침 뒤 그대로 · 가로 넘침 0 · 앱 오류 0. 좁은 화면에서 글이 어색하게 접히면 스크린샷으로 확인한다.

## 7. 커밋 · 올리기
- `npm test` 전부 통과를 본 뒤 커밋한다. 버전마다 따로, 한국어 구어체로 무엇이 달라지는지 쓴다 (종류별 머리말은 0번 표).
- 커밋 설명에 가게 이름 · 실제 근무 날짜 · 개인 정보가 없는지 본다. 저장소는 공개다.
- **올리기(push)는 은월이 말할 때만.** 올린 뒤 `https://sasaway.github.io/life-dashboard/js/version.js` 가 새 버전을 내보낼 때까지 확인하고 보고한다. "앱에 안 보인다" 고 하면 안 올린 커밋이 있는지부터 본다.
- x.9 버전은 올린 뒤 태그 `vX.9` 를 남긴다.

## 8. 마지막 보고 (짧고 쉬운 한국어, 반말)
1. 무엇을 바꿨는지 (버전별)
2. 계획과 달라진 것 · 스스로 정한 것 · 확인하지 못한 것
3. 폰에서 확인하는 법 (설정 맨 아래 버전 글자부터)
4. 다음 할 일 (은월 · Cowork · 다음 버전)

## 9. Cowork 로 넘기는 글
은월이 달라고 하면 코드 블록 하나로 출력한다. Cowork 는 앱 코드를 못 보고 Notion · 시트 · 캘린더 · 브리핑을 맡는다. 이 순서로 쓴다:
1. 지금 상태 — 버전 · 커밋 번호 · 테스트 개수 · push 여부 · Notion 기준 시각
2. 무엇이 바뀌었나 — 은월이 화면에서 보게 되는 것
3. 시트가 어떻게 바뀌었나 — 탭마다 줄 수 · 글 · 빈칸 (칸 수 · 순서가 그대로인지 꼭 적는다. 안 바뀌었으면 안 바뀌었다고)
4. Cowork 가 할 일 (읽기만 하는 확인 → 브리핑 → 캘린더 → 은월 허락 뒤 Notion)
5. 은월에게 물어볼 것 (정하지 않고 남긴 것, 지난 버전에서 넘어온 것 포함)
6. 다음 Claude Code 프롬프트로 넘길 것
7. 하지 말 것 (앱 코드 · 앱이 적는 시트 탭 · 허락 없는 Notion 수정)
